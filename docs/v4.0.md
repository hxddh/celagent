# celagent 4.0 — Goal Loop 实现合同

> 版本 **`4.0.0`**。本文件是 4.0 的实现合同：保证什么、不保证什么、对象怎么排、怎么验证。
> 配套：`README.md`（用户视角）、`docs/architecture.md`（架构）、`HANDOFF.md`（接手）。

## 1. 目标

3.0 让 agent 能派出 agent，但每个 agent 仍然“说完就停”。4.0 把“再催一遍”交给 runtime：

- 用户给一个目标和一条验收命令；
- agent 在 goal worktree 里尝试；每轮结束，runtime 在 agent 之外跑验收；
- 没通过就把失败输出喂回同一个 session，继续；
- 只有验收 exit 0 才算完成；预算/墙钟/尝试数/同一失败 ×3/改测试时停或问人；
- 通过后仍然由人 review、合并。

4.0 不引入 mission、task DAG、coordinator、reviewer 角色或审批状态机。

## 2. 对象布局

goal 状态（本机 `~/.config/celagent/`）：

```text
goals/<id>/goal.json       目标、验收命令、状态、attempts、cost、lastCheck
goals/<id>/GOAL.md         给 agent 读的目标与约束
goals/<id>/checks/*.log    每次验收的完整输出
goals/<id>/answer.json     人回答 blocked 问题的内容
worktrees/<id>/            goal worktree（默认）
```

会话仍是 2.0 的对象，session id = goal id：

```text
sessions/<id>/manifest.json
sessions/<id>/segments/...
sessions/<id>/journal/...
sessions/<id>/workspace/...
```

`goal.json` 关键字段：

```json
{
  "id": "goal-...",
  "objective": "把 npm test 修绿",
  "accept": "npm test",
  "status": "running|blocked|done|stopped|error",
  "attempts": 1,
  "budgetUsd": 5,
  "maxAttempts": 8,
  "deadline": "2026-11-15T02:00:00.000Z",
  "protect": ["tests/**", "test/**", "**/*.test.*", "**/*.spec.*"],
  "failureStreak": 0,
  "lastCheck": { "exitCode": 1, "hash": "...", "output": "..." },
  "blockedQuestion": null,
  "cost": 0.42,
  "sessionId": "goal-..."
}
```

## 3. 循环

goal loop 是一个 Pi 扩展，长在普通 TUI session 里，不是新 daemon：

```text
session_start（TUI 启动 / watchdog 拉起）
  → baseline：跑验收
      通过 → done（不烧 token）
      失败 → prompt(goal + baseline 输出)

agent 工作（可 attach；可用 delegate 派子 agent）
  → agent_settled（Pi 没有自动工作）
  → 跑验收
      通过 → done
      失败 → guards
         未触发 → prompt(goal + 最近失败输出 + 第 N 次)
         触发   → stopped / blocked

blocked
  → 人 celagent goal answer <id> "..."
  → watcher 注入回答，继续同一 session
```

- 用 `pi.on("agent_settled")` 判定一轮结束；不用 `agent_end`，因为后者还可能自动重试/压缩。
- 用 `pi.sendMessage({ triggerTurn: true })` 注入下一轮；消息带 `customType: "celagent-goal"`，在 transcript 里可见。
- 每个 prompt 只带最近一次验收输出（截断 6000 字符），不塞整段历史；上下文不足时 Pi 自己压缩。
- agent 需要人决定时，最后一行写 `BLOCKED: <问题>`；扩展检测到就转 blocked，不再烧 token。

## 4. 状态机与守卫

```text
running ──验收通过──> done
   │
   ├─ attempts >= maxAttempts ──> stopped
   ├─ now >= deadline ──────────> stopped
   ├─ cost >= budgetUsd ────────> stopped
   ├─ 同一失败 hash ×3 ─────────> blocked
   ├─ 保护路径被改 ─────────────> blocked
   └─ 其他失败 ─────────────────> running（下一轮）
```

- `attempts` 在发出 prompt 时 +1；baseline 不计。
- `failureStreak` 按 `(exitCode, 归一化输出)` 的 hash 连续相同计数。
- `cost` 来自 `message_end` 的 usage；provider 不上报 cost 时预算退化为 attempts/deadline。
- blocked 时 goal 不烧 token；watcher 每 1.5 秒看一次 `answer.json`。
- `answer` 里的“允许/可以/同意/allow/yes”会把 `allowProtected` 设为 true；其他回答不会。

## 5. 验收与防作弊

- 验收命令在启动时固定进 `goal.json`；agent 不能改。
- 验收在 agent 之外的进程里跑：`/bin/sh -c <accept>`，cwd 是 goal worktree，超时默认 10 分钟；POSIX 下杀整个进程组。
- 每次记录 exit code、耗时、输出 hash、完整日志；`goal status` 显示最近一次。
- 默认保护 `tests/**`、`test/**`、`**/*.test.*`、`**/*.spec.*`；这些路径有改动 → blocked，人回答“允许”才继续。
- 验收通过但保护路径被改，同样 blocked——不能用改测试通过。
- **局限**：如果 agent 改 `package.json` 的 test script，`npm test` 的含义会变。4.0 记录并高亮这类改动，但不宣称验收不可欺骗；最终仍由人 review diff。

## 6. 接口

```bash
celagent goal start "<objective>" --accept "npm test" \
  [--cwd dir] [--budget 5] [--max-attempts 8] [--max-hours 2] \
  [--protect "tests/**,test/**"] [--in-place]

celagent goal status [id]        # 不带 id 时列出
celagent goal list
celagent goal answer <id> "..."  # 只在 blocked 时
celagent goal stop <id>
celagent goal resume <id>        # watchdog 之外的恢复
```

- 默认创建 worktree + 分支 `celagent/goal/<id>`；`--in-place` 才写当前目录。
- `goal start` 需要 bucket、tmux 和 git 仓库（`--in-place` 除外）。
- `goal status` 显示 attempts、成本、deadline、最近验收、diff、session；`attach <id>` 进入 TUI。
- `goal stop` 写 stopped 并停 supervisor；`goal resume` 从同一 session 继续。

## 7. 崩溃语义

| 崩溃点 | 恢复 |
| --- | --- |
| TUI 被 kill -9 | watchdog 拉起同一 `__tui --goal`；session 从 manifest/checkpoint 恢复 |
| 崩溃在 agent turn 中 | journal 的未完成工具是 `unknown`，不重放；bootstrap 重跑验收，失败则发新 prompt |
| 崩溃在验收中 | 验收进程被杀；bootstrap 重跑验收（命令需可重入） |
| 崩溃在 blocked | watcher 重新启动，等待 answer.json |
| goal supervisor 被 down | goal 状态保留；`goal resume` 重新拉起 |

- `goal.json` 原子写；`attempts` / `lastCheck` 以最后一次成功写入为准。
- 验收命令的副作用不承诺 exactly-once；文档要求它可重入（测试、typecheck、lint）。

## 8. 边界

- 不自动 merge/push/deploy；goal 只产出已验证的 diff 和日志。
- 不做多租户；不做跨 goal 记忆；不做 Web UI。
- 不做“没有验收命令的自主循环”：没有 `--accept` 不允许 start。
- 不把 trigger 当 goal：trigger 每次开新 session；goal 是同一 session + 状态 + 验收。
- goal session 里可以 `delegate` 子 agent；子 agent 的结果仍由 goal session 汇总。
- 不建议在 goal session 里 `/new` 或 `/fork`；goal 绑定原始 session id。
- Windows 的验收进程组终止是 best-effort；4.0 主支持 Linux/macOS。

## 9. 验证记录

自动化：

- `tests/v4-goal.test.mjs`：验收 exit/output/timeout、五种守卫、保护路径、状态/GOAL.md、prompt 渲染。
- `tests/v4-extension.test.mjs`：假 Pi 驱动 `session_start` / `agent_settled`，验证 baseline 通过不烧 token、失败自动重试、同一失败 ×3 → blocked、回答后续跑。
- `tests/v2-supervisor.test.mjs`：`goalId` 传给 `__tui`，state 记录 goalId。
- `npm test`：136 tests / 129 pass / 7 skip（2026-11-14，Node 22/26 双跑）。
- `node --check` / `bash -n` / secret scan 全通过。

未在本次环境验证：

- 真实模型下的完整 goal 循环（本 orb 没有 bucket 配置、aws CLI 或模型 key）。
- 长循环的上下文压缩、真实 flaky 测试、provider 不报 cost 时的预算退化。
- 2 个并行尝试的成本/质量、protected path 作弊的实际发生率。

这些是 4.0.0 之后的 benchmark 项，不能当作已成立。

## 10. 与 4.1 的关系

- **Ship Pipeline**：goal 产出已验证 diff 后，自动开 PR/看 CI；仍不自动 merge。
- **Live Workspace**：goal 可以跑起服务、端口、截图；验收从测试扩展到“页面能打开”。
- **Memory**：跨 goal 的决策/失败记忆。
- **Web/URL**：goal 状态的远程查看。
