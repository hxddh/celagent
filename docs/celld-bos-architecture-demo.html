② 术语速览 — 看懂架构图需要的 8 个词 ▶ 点击展开
术语一句话解释
celagent本产品的名字:一个终端里的 AI 编程助手(复用 Pi 引擎的交互能力)
Celld自托管的分布式运行时:让"会话/任务状态"存在节点上,可休眠、可迁移、可跨机器访问
BOS百度对象存储(S3 兼容):云端存数据的服务,本产品用它做会话的权威备份
双写每轮对话同时写两处:本地缓存(快)+ 云端权威(稳),互不依赖
worker 缓存Celld 节点上的本地副本,读取快(~148ms),可随时从 BOS 重建
CAS / ETag乐观锁机制:写入前比对版本号,版本变了就拒绝——防止多人同时写覆盖彼此
RPO=0零数据丢失:任何时刻出故障,已确认的对话一条都不丢(因为 BOS 是权威)
turn_end 钩子每轮对话结束时的自动回调,触发"双写保存"动作
术语在页面中保留原样使用(不简化),此处提供解释 — 既保持技术准确性,也方便非技术读者对照阅读。
③ 三条数据路径 — agent 的"手"和"大脑"分开走 ▶ 点击展开
路径谁在操作 交互对象是否经过 Celld/BOS丢了会怎样
A. 工具文件操作 bash / read / write / edit / grep / find / ls 本地文件系统(你项目里的代码/文件) 完全不经过 — 就是普通本地读写,改完立即生效 与 Celld/BOS 无关 — 需自行 git 提交保护
B. 对话记忆(持久化) celagent 每轮 turn_end 钩子 双写:Celld 本地缓存 + BOS sessions/*.json 这是 Celld/BOS 参与的唯一路径 BOS 是权威 — 本地/节点全丢也能从 BOS 找回
C. 运行时态 pi 引擎 / 配置 本地文件:agentDir 会话 JSONL、settings.json、凭证引用 不经过(纯本地) 本地丢失不影响 BOS 里的对话历史
一句话: agent 的"手"(工具)只碰本地文件系统;Celld/BOS 管的是"大脑"(对话记忆)。 你在项目里让 agent 改代码 = 本地写盘;你关掉它/换电脑 = 记忆从 BOS 找回(但改过的文件需要 git)。
④ 具体写入 Celld / BOS 的是什么 — 每轮对话的"记忆快照" ▶ 点击展开
每轮对话结束,celagent 把这一轮的对话记录(不是文件、不是工作区)打包成一条 JSON 写入两处。 以下为结构示例(字段结构真实,内容为演示):
// Celld worker 缓存结构 (会话经双写路径时, 节点 18090 的形态) — msg 截断 200 字符, 无 role // 注: 实录会话由 BOS 直写生成, 未走 worker 缓存路径; 此结构为经双写时的真实形态 { "id": "sess-demo-xxxxxxxx", "turns": [ { "turn": 1, "msg": "继续分析项目的架构部分,重点关注 bin/celagent-tui.mjs 的实现细节", "ts": 1786352334751 } ], "updatedAt": 1786343740759 // 字段形态示例 (worker 缓存含 updatedAt; BOS 权威源不含) } // 实测: BOS 权威源 (sessions/sess-demo-xxxxxxxx.json) — 完整记忆 // turn1 为演示脚本 (真实产品 turn_end 只写 assistant 轮); content/toolResults 为完整字段 { "id": "sess-demo-xxxxxxxx", "turns": [ { "turn": 1, "role": "user", "msg": "继续分析项目的架构部分,重点关注 bin/celagent-tui.mjs 的实现细节", "ts": 1786352334751, "content": [ // 完整内容块 (thinking/text/toolCall 全量) { "type": "thinking", "thinking": "完整推理过程…" }, { "type": "toolCall", "name": "bash", "arguments": { "command": "ls" } } ], "toolResults": [ // 完整工具结果 { "toolName": "bash", "content": [{ "type": "text", "text": "src\nbin" }] } ] } ] }
字段含义Celld 缓存BOS 权威
turn轮次序号(1,2,3…)✓✓
role发言角色:user / assistant✗ 不存✓
msg摘要文本(供恢复注入与 worker 缓存,各段带长度上限)截断 200 字符完整保存
content完整内容块:thinking / text / toolCall✗ 不存✅ 完整
toolResults完整工具结果(本地 JSONL 不存)✗ 不存✅ 完整
ts时间戳(ms)✓✓
updatedAt会话最后更新时间✓—
不存什么: 不存你的项目文件、不存工具产生的文件内容本身 — 只存对话记录(谁说了什么、调了哪些工具、结果摘要)。 写入的 msg 形如:"分析一下… [工具调用: bash("ls")] [工具结果: bash: src bin docs…"
注:真实产品钩子(turn_end)只存 assistant 轮;user 轮仅出现在本页演示脚本中。 摘要长度上限:工具调用 ≤100 字符、工具结果 ≤300 字符(汇总拼接后写入)。
为什么 worker 缓存截断 200 字符? 缓存写入走 HTTP GET,msg 作为 URL 参数传递 — URL 长度受限,且中文经 URL 编码后膨胀约 3 倍(200 中文字符 → 约 1080 字符 URL)。 截断是安全的:worker 只是缓存(丢了可从 BOS 重建),BOS 权威源永远存完整内容。

⑤ 常见问题 — 存什么 · 性能 · 之前在哪 ▶ 点击展开
Q1: 写到 BOS 的是 agent 会话的"所有内容"吗?
BOS 存完整内容块 + 完整工具结果,同时保留摘要 msg 供快速注入。完整会话仍以本地 pi JSONL 为准(含 user 轮):
内容BOS(权威)本地 JSONL
assistant 回复文本✅ 完整✅ 完整
thinking 推理过程✅ 完整✅ 完整
工具调用(名称+完整参数)✅ 完整✅ 完整
工具结果✅ 完整❌ 不存
user 输入⚠ 真实产品不写(turn_end 钩子只存 assistant 轮);本页示例数据含 user 轮(演示脚本直接写入)✅ 完整
摘要 msg(供恢复注入)✅ 保留—
注:BOS 的 toolResults 完整存储甚至比本地 JSONL 更全(JSONL 不持久化工具结果);两者互补。
Q2: BOS 写一次要 ~0.84 秒,性能问题怎么解决?
写延迟被完全挡在对话之外 — 对话轮结束,turn_end 钩子毫秒级返回,不等待 BOS:
机制作用
异步 fire-and-forget 队列写 BOS 不阻塞对话,用户无感知
串行队列 + 限长 50防堆积;队列过长丢最旧并警告
CAS 冲突重试(3 次,退避)网络抖动/并发时不丢数据
20s 超时防网络黑洞卡死队列
退出时 flush关程序前等队列写完,最后几轮不丢
Celld 本地缓存(~148ms)快路径立即可读;BOS 是慢但稳的权威源
Q3: 没有 Celld/BOS 之前,agent 会话存在哪?
纯本地文件系统。pi 原生(以及传统 CLI agent)把会话写成本地 JSONL 文件 (~/.pi/agent/sessions/.../*.jsonl),每轮 append 一行;恢复 = 读本地文件。
本地即全部:换电脑 / 删目录 / 磁盘损坏 = 会话永久丢失。

celagent 的增量不是"不用本地了",而是加了一层云端权威副本: 本地 JSONL(pi 引擎运行时态) + Celld 缓存 + BOS(权威副本) — BOS 解决本地单点故障(换机/丢失/节点挂),代价是 ~0.84s 写延迟(2026-08-10 采集样本),用异步队列隐藏。
Q4: agent 能主动用 BOS 做什么? — 记忆增强工具(实测)
agent 对话中内置两个 BOS 记忆工具,可主动调用(不只是被动被持久化):
工具功能实测结果
history_search 跨会话检索 BOS 历史记忆:按关键词/会话/条数,返回匹配轮次片段(会话/轮次/角色/时间/内容) ✅ 真实 LLM 对话中调用,搜"持久化"命中 4 条历史记忆
session_snapshot 显式记忆锚点:把当前会话状态保存为 BOS 快照(snapshots/<name>-<ts>.json) ✅ 快照轮次随对话增长(2 轮 → 4 轮)
意义:agent 从"只记得当前会话"升级为"可检索全部历史" — 例如问它"我之前关于并发问题的讨论",它能主动搜索 BOS 并引用结论。

Ⅲ 结论 价值评估
⑨ 价值评估 — 一句话定位 + 诚实评估
一句话定位: BOS = 保数据(权威持久层,跨机器防丢失) · Celld = 保执行(分布式运行时) — "会话永不丢"由 BOS 兑现(真实需求,已验证);Celld 提供节点发现/休眠唤醒/任务状态机(多机场景核心,)。
组件承载的数据类型实际价值价值评估(诚实版)
BOS 对象存储 sessions/<id>.json(权威对话,完整不截断,38 个)、cells/*/ltx + own.json(Celld 分布式状态,215 个)、deploy/agent-runtime(worker 代码包,15 个) 会话跨机器/防丢失(RPO=0)、并发安全(CAS)、换机器/删本地/节点全挂都能找回 ✅ 核心价值,真实需求,故障注入实测验证(节点全挂可写、恢复 60/60)
Celld 双节点 worker SQLite 缓存 session:<id>(截断 200 字符)、cell 状态(LTX/own 经 BOS)、deploy 里的 worker 执行环境 低延迟本地缓存(~148ms 实测)、节点自动拉起/故障转移、worker 执行器 ✅ 执行层价值:节点发现/状态迁移/休眠唤醒/任务状态机 — 多机场景核心组件;单机场景价值有限
celagent (TUI) 运行时态:pi 引擎会话(agentDir 独立目录)、配置 settings.json、BOS 凭证引用(~/.aws/credentials) 复用 Pi 引擎全部能力,只替换持久化层;独立品牌、不 fork ✅ 交互层,复用成熟引擎,专注持久化差异化
架构结论: BOS 保数据(权威,跨机器/防丢失,RPO=0) · Celld 保执行(分布式运行时:节点发现/休眠唤醒/任务状态机) · agent 可用 BOS(记忆工具:history_search/session_snapshot) — 分层并存:数据层与执行层分离。⚠️ 本页为演示 + 真实数据混合:对话脚本为演示用途; 对话为 2026-08-11 真实会话实录;对象大小为 5s 轮询监控实测 (26 轮 24 观测点, 缺失插值); worker/read/write 延迟为 2026-08-10 采集样本;自动播放按序回放,不重复访问 BOS; 数据保存在 sessions/sess-demo-xxxxxxxx.json (bucket 为用户私有 BOS bucket)
